Requisiti funzionali – Interazione e stato UI

1. Stato iniziale (pre-tutorial / pre-scenario)

Prima dell’ingresso nel tutorial/scenario:

Tutti i pulsanti UI NON devono risultare visivamente cliccabili (stato attivo).

Nessuna interazione deve produrre effetti:

niente eventi

niente azioni

niente cambi di stato

Obiettivo: UI “disattiva” , logica disabilitata.

2. Gestione delle varianti (setVariant)

La funzione setVariant:

deve essere invocabile anche al di fuori dei trigger

deve poter essere chiamata:

via codice diretto

via eventi custom

via stato globale

Non deve dipendere esclusivamente da collider, raycast o trigger fisici.

3. Punto di rotazione degli oggetti

Per ogni oggetto deve essere configurabile il pivot di rotazione:

Opzioni supportate:

Centro del bounding box

Origine locale dell’oggetto

La scelta:

deve essere per-oggetto

deve essere configurabile (flag, enum o proprietà)

Il sistema di rotazione deve:

rispettare dinamicamente il pivot selezionato

non richiedere duplicazione dell’oggetto

4. Eccezione di input – oggetto pavimento.glb

Se l’utente clicca pavimento.glb per:

posizionare il target della telecamera

Allora:

il pulsante “rotella” (rotazione) NON deve avere alcun effetto

In pratica:

click su pavimento.glb → solo logica di camera target

input di rotazione disabilitato finché il target è il pavimento

Vincoli impliciti (da rispettare)

Separazione netta tra:

stato visivo della UI

stato logico di interazione

Input handling contestuale all’oggetto selezionato

Nessun side-effect non intenzionale sugli altri controlli
